# The Odin migration

Colophon 1.0.0 (Rust and Slint, on `main`) is rebuilt in Odin on the branch `odin-migration`, one pull request per slice, until it does everything 1.0.0 does. This file is the plan, the parity list, and the record of what is done and decided. How the work runs is in [`AGENTS.md`](../AGENTS.md).

Status: approved by Florent on 2026-10-13; in progress.

## Why

A prototype built in a day (Odin, SDL3, every pixel drawn by the app) matched the design mockups, felt faster than 1.0.0, and weighed 2.4 MB with its fonts. Odin keeps the native tool feel of the brief with a far smaller and simpler stack, and Open Media Stack now has its own ID3 library in Odin, [odid3](https://github.com/OpenMediaStack/odid3).

## Open questions for Florent

- **AccessKit as a dependency** (from the accessibility spike), for slice 45, vendored in `libs/accesskit` with its licenses. AccessKit is MIT or Apache 2.0 (plus a BSD-style Chromium license for part of it, and about 160 Rust crates built in, which the About dialog will list), and is what Slint used for 1.0.0. It ships prebuilt C libraries for macOS arm64 and x86_64 (static, 10 MB for arm64, joined with `lipo` for one app), Windows x86, x86_64 and arm64 (a 360 KB DLL for x86_64), and Linux x86 and x86_64 (static, 46 MB for x86_64); Linux arm64 needs building from source with Rust. Linked statically, only what is used stays: the spike's binary weighs 1.0 MB, 636 KB stripped. Saying no means writing Colophon's own NSAccessibility, UI Automation and AT-SPI bridges, or shipping without screen readers, which leaves the parity line of slice 45 unticked. Yes or no?
- **Windows menu bar and context menus: drawn or native**, for slice 44c. The brief's design column says "Menu bar inside the window" for Windows and Linux, with the `menu_bar` token; its Implementation column, the Rust stack's, says muda's native bar on Windows (in system colours) and native context menus on macOS and Windows, which is what 1.0.0 did. Slice 44a already draws the bar on Windows and Linux, and 44b gave macOS its native bar. This reopens the 2026-10-14 menus spike's plan for Windows (`SetMenu`, `SDL_SetWindowsMessageHook`, `SDL_HINT_WINDOWS_ENABLE_MENU_MNEMONICS`). Two choices:
  1. **The Windows bar: drawn or native?**
     - **Drawn** (recommended): matches the brief's design column and Linux, follows the light and dark theme, never stops the frames, and runs under the same tested frames. Screen readers see it through the accessibility tree of slice 45, so it depends on the AccessKit answer above. 44c shrinks to Alt, the underlined mnemonics, and the titles joining the Tab order, which Linux's drawn bar gets too. Not what 1.0.0 did on Windows.
     - **Native through `SetMenu`**: Windows' own look, Narrator and Alt for free. It is code no agent here can run (the CI only renders a frame headless, so Florent would be the only tester), the bar cannot follow Colophon's theme, and Win32 menus run a modal loop that stops the frames while one is open.
  2. **The context menus on macOS and Windows: drawn or native?** Drawn (recommended) is what Linux does and what the toolkit already has; native gets the system's look and VoiceOver or Narrator for free, with the same modal loop, and asks more of every call site.

  A "drawn" answer to either rewords the parity line "Native menus and context menus as the brief's platform adaptations say", slice 24's "until slice 44 makes theirs native" and the spike's row, and 44c is no longer a `feat(platform)` slice.

- **The text stack** (from the text spike), for slice 20 and every screen. Options:
  1. **HarfBuzz and FreeType**, the C libraries browsers use (MIT and FreeType licenses). HarfBuzz shapes OpenType and Apple's `morx` fonts alike; FreeType rasterizes any `glyf` or `CFF` font. Costs: both built for each platform in the CI; bindings to CoreText, DirectWrite and fontconfig to find fallback fonts per run; on macOS, PingFang is unreadable, so CJK falls back to Hiragino; colour emoji need libpng and zlib for Apple's and Noto's bitmap emoji, and our own drawing for Windows' COLRv1 emoji font; a bidirectional reordering of our own. The size is not measured. Closest to 1.0.0.
  2. **`kb_text_shape` and `stb_truetype`**, already in Odin's vendor folder, with a fixed list of system fonts known to work (Hiragino for CJK, SF Hebrew or Arial Hebrew; not tried on Windows and Linux) or fonts bundled in the app (Noto Sans Arabic and Hebrew, and CJK fonts per region: Japanese, simplified and traditional Chinese, Korean, several megabytes each). Costs: two fixes upstream in `kb_text_shape` (the cmap lookup, the equivalences that break Greek), no Arabic joining with `morx`-only system fonts (so Arabic needs a bundled `GSUB` font), no colour emoji, and the same bidirectional reordering.
  3. **Latin, Greek and Cyrillic only for now**, other scripts shown as boxes, and one of the above later. Not parity with 1.0.0.

  The agents' recommendation is 1. Which one?

## Slices

Each slice is one pull request, in this order unless a slice says it can move. A slice is ticked in the pull request that completes it. Rust file names point at what to port; their tests are the spec.

### Phase 4: audio

- [x] **42a. `feat(audio): player`.** The `audio` package plays files through miniaudio (`vendor:miniaudio`, a new dependency of Odin's own vendor tree, built for the CI on Linux and macOS when missing, and checked on Windows): `Player` decodes on the audio thread to the device's rate and channels, plays, pauses, resumes, stops, seeks to a position, tells how far it has played and whether it has played to its end, and sets the volume; A file is read whole into memory and closed at once, and decoded from there (over half a gigabyte is refused): a file held open cannot be replaced by saving on Windows, however it was opened, and saving renames a copy over the file. `read_waveform` decodes a whole file into the waveform's builder in chunks, cancellable from another thread. Tested on a silent device that keeps time (miniaudio's null backend), so no sound card is needed: an MP3 plays, holds and goes on, seeks, reports its end, files that are no audio or are missing say why, and truncated and mutated files never panic. Ported from `player.rs` and its tests; the engine's `Output` (slice 14) is adapted in 42b.
- [x] **42b. `feat(app): player`.** The player bar under the table, shown while a track plays or is paused through an output: previous, play or pause, next, the title and artist, the position and the duration as times, a bar to click or drag along for the position (the waveform of 43b takes its place), and the volume, which goes first when the bar is under 800 points wide. - [x] **43a. `feat(audio): waveform pyramid`.** The `audio` package starts with the min/max pyramid: `Waveform_Builder` takes interleaved samples in chunks of any size (a frame may be split between two), mixes the channels, and makes the peaks of 256 frames, each level half as many as the one before; `peaks` gives any number of them across the track at once, read from the level that keeps neighbours out of a share; `loudness` is the root mean square. Ported from `player/src/waveform.rs` and its tests, plus chunked input and short or odd tracks. Pure computation: no decoder yet, and no dependency.
- [x] **43b. `feat(app): waveform`.** The waveform of the playing track takes the place of the position bar: a thread decodes the file with `read_waveform` when a track starts (a new track stops the reading, which is freed once its thread has ended), the UI thread takes it in, and draws bars of 2 points every 3, as loud as each share of the track sounds beside the loudest, flat until it is read, the part played in the accent colour; a click or a drag along it seeks. ## Risks

- **Accessibility** has no Odin library: AccessKit's C API works from Odin on macOS (spike 3). Windows and Linux are still to be tried, in slice 45 at the latest.
- **SDL3 on Linux** has no package on the CI's Ubuntu image: it is built from source and cached.
- **Pixel captures across systems** can differ slightly even with the software renderer: the comparison has a tolerance, and a capture that differs only on one system is investigated, not regenerated blindly.
- **Text** beyond Latin, Greek and Cyrillic needs a text stack Florent chooses after spike 4; until then such titles show as boxes.
